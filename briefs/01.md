## The two findings that shape the whole collection

**1. An account created with `POST /admins/users` is not the account a reader has.**
Every other collection seeds its persona that way. Collection 01 cannot leave it
there, because that endpoint also creates `<Name>'s leaderboard`, and a Free
account may hold exactly one leaderboard. An admin-created persona therefore opens
**Leaderboard Limit Reached** where a reader opens the create form, which is the
second half of 01.5. The same endpoint leaves `gender`, `sports` and `position`
empty, which no real signup does, so Profile settings reads *4 highlighted fields
are still missing* instead of the *1* a reader sees - and that count is the subject
of 01.6.

`scripts/seed-01.mjs` therefore creates the account that way and then brings it to
a reader's state: it sets a password with Identity Toolkit's `accounts:update`,
fills Step 1's fields with `PUT /users/:id`, and deletes the leaderboard. The
result was compared against a real signup on screen: same two default teams, same
`1 highlighted field is still missing.` on both sections, same Change Password
panel.

**2. These flows consume the state they document.** An address can only sign up
once. The wizard runs once per account. An account can only be deleted once. That
is why the collection has seven accounts and why most of the seed is teardown
rather than setup.

### 01.1's scope, and the one thing that forced a decision

01.1 documents **email and password only**. Google and Apple get one sentence each
and no provider screenshots. It covers email verification and **stops at the screen
asking for the code** - the code being typed and the success state are deliberately
not captured, and `kb-01-signup@` is left unverified by design.

lands on **Step 1, Personal information**, and the code screen only opens after
Step 1 is submitted - `POST /users` then `POST /users/verify-email/request`, both
observed on the wire. So 01.1 cannot reach its own end point without passing
through Step 1, which is 01.4's subject.

01.1 therefore shows Step 1 in two shots and says what it is for in two sentences,
then points at 01.4. That is the minimum needed to reach the code screen; there is
no shorter path.


Two things worth knowing before re-running it:

- **`accounts:update` revokes every token Firebase has issued for that user.** The
  session used to set the password is dead immediately afterwards and has to be
  minted again. That cost one failed run.
- **The seed is idempotent.** A second run reports `already has the password` and
  `no leaderboard, as 01.5 needs`, and makes no writes to the persona. It does
  rebuild `kb-01-reset@` every time, on purpose - Firebase refuses a reset that
  does not change the password, so that account must start each run with none.

## Capture rules for this collection

Five things are specific to these screens and are settled once, in `lib/kb.ts`,
rather than per capture.

1. **The home page's promotional banner is blocked, not dismissed.**
   `GET /promo-campaigns/active?screen=Home` returns whatever campaign is running
   ("Summer competition" today) and renders a full-width banner that moves the page
   down. `blockPromos()` fulfils that request with empty data. Dismissing it
   instead would write the dismissal to the account and make the first run differ
   from the second. Collection 02.5 is the article about promotional messages.
2. **The home page's TRENDING feed is never in a capture.** It is global activity -
   other people's teams, other collections' tournaments - and the style guide
   forbids another persona's data. The two home captures are clipped to the profile
   header instead.
3. **The verification countdown is masked.** "Didn't receive an email? 00:57" ticks
   every second. Once it reaches zero the digits become a **Resend** link, which is
   stable and is not masked.
4. **`unstickHeader()` before any tall clip.** The app's header is
   `position: sticky`, so on a screen taller than 900px it paints itself over the
   top of whatever is clipped. The first run of 01.1 lost the "Step 1" label to it.
   A full-page capture is worse: the header lands in the middle of the image.
5. **A list that opens is captured as a viewport, not clipped.** Every dropdown in
   this app is portalled outside its dialog and several open upwards, so a clip to
   the dialog is a floating list on top of a box the reader cannot see. Caught on
   01.5's team-size list and applied to 01.4's three lists too.

Masked in this collection: the verification countdown, "Joined Since August 2026"
in the profile header, and "Created on 28/08/2026" on a leaderboard card. **Not**
masked: the persona's name and address in 01.6's sidebar capture, because that
block is the subject of the article and a mask would black out most of a 255px-wide
clip. Same call collection 12 made about its allowance panel.

**Specs sign in through the form, with a password - never with a minted token.**
A token sign-in leaves Firebase's `providerData` empty, and Profile settings then
replaces Change Password with "You signed in with Unknown. Password changes are
only available for accounts that use email and password authentication." No reader
sees that screen. 01.7 is the exception: it signs in with a minted token, because
its account has no password and none of its captures show that panel.

### 01.7 Deleting your account, and why an account may be disabled

- Persona: `kb-01-delete@`, signed in with a minted token - it has no password, and
  none of its captures show the Change Password panel.
- Preconditions found: deleting removes the Firebase user too. Afterwards the
  address behaves exactly like an address that never existed.
- **The two halves say different things.**
  - Deleting is self-serve, immediate and final. You are signed out on the spot.
  - **Being disabled is not something the app does.** Firebase can disable an
    account, and the sign-in screen then reads *This user account has been
    disabled.* Nothing in Scoryboard reaches that state, so it cannot be
