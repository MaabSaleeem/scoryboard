## Read this first

**Two of the four titles in `config/articles.yaml` describe features this build
does not have.** Both were checked endpoint by endpoint and screen by screen on
staging on 2026-09-02, and both are retitled below rather than dropped. Nothing
is invented and nothing is quietly narrowed: what follows is what the app does.

1. **Comments exist on two screens, not five.** `POST /comments` takes
   `commentType` from the enum `leaderboard | team | match | player |
   tournament` - the API prints that list in its own validation error - and all
   five are accepted and stored. Only **leaderboard** and **team** render a
   comment panel. A match page fires no `/comments` request at all (its FEED is
   the match event list, which collection 10 owns); a player profile fires none;
   no tournament tab fires one either, organiser board or public page. So a
   comment posted against a match, a player or a tournament is invisible to
   every screen in the web app.

   19.1's title, "Commenting on a match, team, player, league or tournament",
   is therefore wrong on three of its five nouns.

2. **A comment cannot be edited and cannot be deleted.** The app's whole comment
   surface is `POST /comments`, `GET /comments`, `GET /comments/:id/replies`,
   `POST|DELETE /comments/:id/like` and the two media paths. There is no
   `editComment` and no `deleteComment` anywhere in the bundle, and a comment row
   carries exactly three controls: **Reply**, a thumbs-up with its like count and
   a speech bubble with its reply count. `PUT /comments/:id` does work over the
   API and nothing calls it. `DELETE /comments/:id` answers
   `401 "Unauthorized to delete this comment"` even to the account that wrote the
   comment - collection 08 found that half first, and it still holds.

   19.2's title, "Editing, deleting and liking comments", is therefore wrong on
   two of its three verbs.

3. **19.1's `free_pro` flag has no basis.** There are two Add Media buttons in
   the bundle. The **match feed**'s checks `membership === Pro` and otherwise
   opens the upgrade modal - that is the gate `config/api.md` records, and it
   belongs to collection 10. The **comment composer**'s checks nothing, its file
   input is `accept="image/*"`, and `POST /comments/media` answers 200 to a Free
   account (measured with `kb-player-19@`, Free, uploading a real file). Nothing
   else in the comment or rating surface differs by plan. There is no dual
   capture in this collection.

Everything in 19.3 and 19.4 matched the map.

## Amended during the run

Written into this file while step 2 was running, and named again in the
end-of-run report. Neither was known when the plan above was first written.

1. **A rating CAN be removed, and 19.3 gained a seventh shot.** The Rate panel

   part of this run and are corrected.

2. **19.2's like captures moved to a different comment.** The plan put them on
   Pat's "New kit arrived this morning.", which carries the image attachment. The

### 19.1 Commenting on a team or a leaderboard

- Persona: **player** (`kb-player-19@`, Free). A Player on KB Comets and an
  Administrator of KB Comment League. Shot 06 is taken as **outsider**
  (`kb-19-outsider@`), who is on neither.
- Preconditions found:
  - Commenting is **members only**, and the app disables rather than hides. A
    non-member sees the whole panel with the textarea, **Comment**, **Add Media**
    and every **Reply** button `disabled`, and no message explaining why. The API
    agrees: `403 "Only team members can comment on or like team content"`, and
    the leaderboard's equivalent.
  - **Leaderboard membership is wider than `config/api.md` says.** That file
    records `isMember` as true for the Owner and Administrators only. A player on
    a team that is *in* the leaderboard may comment too - measured with Rae, who
    is neither. Corrected in `config/api.md`. **Collection 08 already had this
    right**: article 08.5 says "the Owner, an Administrator, and anybody playing
    for one of its teams". Only the API reference was behind.
  - The **Comments** tab is not a route. On both screens it scrolls to a panel
    that sits below every other tab, so the panel is reachable from the bare
    path and the capture does not need the tab.
  - The heading counts **top-level comments only**. A reply is not in it, and is
    not in `GET /comments` either - it lives behind
    `GET /comments/:id/replies`, and in the UI behind **View n more replies**.
  - An attachment is **not an `<img>`**. `GET /comments/:id/media/:filename`
    needs the bearer token, so the app fetches it, makes a `blob:` URL and paints
    it as a CSS background on a bare div. `imagesPainted()` covers background
    images, so the ordinary capture gate holds, but nothing finds it by role.
  - The composer's file input is `accept="image/*"`. Images only, no video.
  - Typing `@` opens nothing. The composer is wired for mentions in the bundle
    and the suggestion list stayed empty on every screen tried, so **mentions are
    not documented**.
- Dual capture: **no.** See "Read this first", point 3.
- Steps:
  1. Open your team and scroll to **Comments**.
  2. Type your comment in the box.
  3. Choose **Add Media** if you want to attach a photo.
  4. Choose **Comment** to post it.
  5. Do the same on a leaderboard - the panel is identical.

### 19.2 Replying to and liking comments

- Persona: **player** (`kb-player-19@`, Free).
- Preconditions found:
  - A comment row carries exactly three controls: **Reply**, a thumbs-up with
    the like count, and a speech bubble with the reply count. Neither icon
    button has an accessible name; their only text is the number.
  - **The thumbs-up changes icon as well as colour.** Outline and
    `text-gray-600` when you have not liked it; filled and `text-blue-600` when
    you have. A locator that matches one SVG path finds the button before a like
    and loses it after, so `likeButton()` matches both paths.
  - Liking is a real toggle and it is reversible:
    `POST /comments/:id/like` then `DELETE /comments/:id/like`. A second POST
    answers `409 "Comment already liked"`.
  - The like count is the **total**, not yours. Pat's comment reads 1 to Pia,
    who has not liked it - the 1 is Ollie's.
  - Replies are collapsed behind **View n more replies** and fetched on demand.
    The panel finishes counting before that fetch lands, so the count alone is
    not a safe gate - `settled08()`'s spinner check is.
  - The reply composer is a **second textarea with the same placeholder** as the
    panel's own. Its **Cancel** button is what tells them apart; the top-level
    composer has none.
  - **Editing and deleting do not exist.** No control, no mutation in the
    bundle, and `DELETE /comments/:id` answers 401 to the author. The article
    says so in its own section rather than burying it.
- Dual capture: no.
- Steps:
  1. Find the comment you want to answer.
  2. Choose **Reply**, write your answer and choose **Reply** again.
  3. Choose **View n more replies** to read a thread's answers.
  4. Tap the thumbs-up to like a comment. Tap it again to take the like back.

### 19.4 How average ratings are calculated

- Persona: **player** (`kb-player-19@`, Free).
- Preconditions found:
  - The average and the count appear in three places, all rendered the same way:
    the match header, a team page header and a player page header. The count is
    a real `<button class="text-blue-400 underline">` and opens the review list.
  - `GET /ratings/:type/:id/summary` answers
    `{averageRating, totalCount, distribution}`. **The distribution is not shown
    anywhere in the web app** - the review list shows each rating instead. The
    article describes what a reader can see and does not mention a breakdown.
  - **The app rounds to one decimal place.** Pia's mean is 4.666..., the API

## Corrections to config/api.md

Appended with today's date, all observed on the wire or in the app:

1. `commentType` is a five-value enum and the API names it in its own error:
   `leaderboard | team | match | player | tournament`. This answers the TODO
   `config/api.md` left against collection 19. Only two of the five have a UI.
2. `PUT /comments/:commentId` exists, answers 200 and edits the comment. Nothing
   in the app calls it. `DELETE /comments/:commentId` still answers 401 to the
   author.
3. `POST /comments/:id/like` twice answers `409 "Comment already liked"`.
4. Commenting on a leaderboard is open to a player on a member team, not only to
   the Owner and Administrators.
5. **`POST /tournaments/:id/referee` sets `isReferee: true` and
   `defaultProfile: "Referee"` on the target account.** That closes the TODO
   collections 09 and 21 both left open about how somebody becomes a referee.
6. `POST /matches/:id/status {"status":"Cancelled"}` **does** work, on a match
   the server auto-finished. On a match finished by an explicit POST it answers
   "Cannot update status of a Finished match", and `PUT /matches/:id
   {"status":"Cancelled"}` then works instead. `config/api.md` says the POST
   endpoint cannot set Cancelled at all.
7. `POST /ratings` from an account that has already rated that entity replaces
   its rating: `totalCount` does not move.
8. **A rating is edited and deleted from the reviews list, not from the Rate
   panel.** The kebab on your own review row offers **Edit** and **Delete**;
   Delete fires `DELETE /ratings/:id` and is not confirmed. Written into
   `config/api.md` after a first, wrong version of that entry claimed no control
   called it.

## Open questions

1. **The Team panel's subject dropdown is labelled "Player".** It lists teams,
   defaults to the home team and works correctly; only the label is wrong. It is
   visible in shot 05, so 19.3's "If it does not work" names it in one sentence.
   Assumed to be a defect rather than a meaning; worth a ticket.
2. **Comments can be posted against a match, a player and a tournament over the
   API and nothing renders them.** Either the UI is unfinished or the enum is
   ahead of it. Assumed unfinished. Nothing in this collection writes one, and
   19.1 does not mention that the API accepts them.
3. **`GET /comments/stats` returns `{totalComments, totalReplies}` and no screen
   calls it.** Not used and not documented.
4. **The rating `distribution` in the summary response is a five-key histogram
   repeated once per rating** - three ratings come back as an array of three
   identical objects. That looks like a defect in the response shape. Nothing
   reads it, so nothing is documented from it.
5. **A comment is permanent even to a Scoryboard administrator**, as far as this
   collection could tell: there is no admin comment endpoint in `config/api.md`.
   19.2 tells the reader a comment cannot be taken back and does not offer a
   support route, because none was found.
6. **Deleting a rating is not confirmed.** The menu item fires the DELETE on the
   click, with no "are you sure". That is the same pattern collection 18 found on
   deleting a chat message. 19.3 warns the reader in one line. Assumed
   deliberate; worth a ticket alongside question 1.
7. **Why can a comment never be deleted when a rating can?** Both are user
   content, both have a working DELETE in the API, and only the rating has a
   control. Assumed the comment UI is unfinished rather than the delete being
   deliberately withheld. Nothing is documented from the assumption.
